Debugging 1 ms radio slot timing in a wireless robot loop

How a 10-second hurdle test exposed four timing failures, what the traces showed, and how to verify the fixes.

What to measure

In the wireless hurdle test, a simulated robot sent observations through the user equipment (UE) and base station (gNB) to a TensorRT policy. Actions came back through the radio path and the robot installed them at a physics boundary. The OCUDU channel broker applied the radio channel to in-phase and quadrature (IQ) samples. The broker and TensorRT shared a GPU, while the simulator advanced physics and proportional-derivative (PD) control on a 1 ms wall-clock schedule.

  • Radio progress. At 23.04 million IQ samples/s and 15 kHz numerology, one nominal 1 ms slot contains 23,040 samples. Report how many slot equivalents the broker completes in uplink (UL) and downlink (DL) and how far completion trails the nominal clock.
  • Radio processing time. Time a full batch from broker call entry to return. A call over 1 ms is a processing overrun. When a nominal slot spans fragments, the broker counter uses sample-proportional processing estimates. Report those counters separately from traced full-batch durations and from gNB MAC timing.
  • Robot timing. Count physics steps, PD updates, and distinct new target installations separately. The policy receives an observation every 20 physics steps. PD can reuse the last target on every tick until another action arrives. Zero added delay still includes observation preparation, radio transit, inference, and action pickup.

1. Physics and PD ran below 1 kHz

Failure pattern. Physics and PD each averaged 964.5 Hz even though the median physics tick gap was about 1 ms. The physics gap at the 95th percentile was 2.24 ms, and new targets arrived at 48.2 per second.

Analysis. Comparing scheduled tick boundaries with actual completions exposed delays in the tail. Preparing observations on the physics thread lengthened some ticks. Linux wake-up coalescing could also delay a sleep past its scheduled boundary.

Solution. Move observation preparation to a separate worker. Pass it the state captured at the tick boundary and tighten timer slack on the physics thread.

Why it worked. Physics and PD can continue while the observation is prepared, and the thread can wake closer to its scheduled time. The follow-up recorded 9,999 physics steps and PD updates each over 10 seconds. Physics gap p95 fell to 1.16 ms, while distinct new targets reached 49.8 per second.

2. Radio progress dipped in short windows

Failure pattern. Early one-second bins fell below 1,000 slots/s. In a later run, the first four seconds cleared that rate and the run averaged about 1,003 slots/s per direction, yet the ninth bin fell to about 996 UL and 997 DL. Catch-up elsewhere in the window hid the dip in the average.

Analysis. Scheduler traces showed radio work ready to run while another task occupied the CPU. One gNB I/O thread waited about 3.55 ms alongside Sionna work. Broker waits over 2 ms also coincided with background health checks. Some trace rings overran, so those events identified specific contention without providing a complete count.

Solution. Give radio I/O and broker processing suitable CPU placements and separate the Sionna worker from those threads. Verify the effective CPU affinity of the running threads, including any spawned during setup.

Why it worked. Separating competing work reduced time spent runnable but off CPU. In the untraced follow-up every one-second bin exceeded 1,000 slots/s in both directions. The broker still recorded processing overruns, which called for a different measurement. Linux ftrace documentation.

3. The broker exceeded 1 ms during inference

Failure pattern. With the broker delivering roughly 1,000 slots/s, individual calls still took more than 1 ms. The first shared-GPU changes brought a no-MPS control with 473 processing misses down to 41 in a 10-second run. Those remaining misses called for a per-call trace.

Analysis. In a reproduction, all 42 traced full-batch calls over 1 ms overlapped TensorRT inference, and 34 spent over 0.75 ms in CUDA stream synchronization. The longest runnable CPU wait among those calls was 0.037 ms. The processing CPUs had no trace loss. This pointed to a wait for GPU work, and device events could only time work after the first event began.

Solution. The first changes put the broker and TensorRT on the same CUDA Multi-Process Service (MPS) server, gave the broker high-priority streams, and mapped its per-slot metadata and output buffers. To address the remaining contention, limit TensorRT's active GPU threads and verify both MPS membership and the effective multiprocessor count. The selected cap was 35% for this setup.

Why it worked. MPS lets the two processes submit work through a shared GPU scheduler. Priority favors broker work when resources become available. Mapped buffers remove separate transfers for metadata and output, while the cap limits how much GPU execution capacity TensorRT can occupy. The 35% cap with the earlier broker reduced the count to two misses in one traced run. A 25% comparison had more misses, so the cap was chosen from the measured workload. NVIDIA MPS resource provisioning.

4. Profile refreshes still caused stalls

Failure pattern. A narrower trace at the 25% cap found 12 full-batch overruns during live channel-profile updates. These events spent most of their time before the final stream synchronization.

Analysis. Probes around the refresh API call measured 0.72–1.04 ms in the copy of device state into pageable host memory. The following explicit refresh sync took only a few microseconds. A CUDA copy with an asynchronous API name can still block the host when pageable memory is involved. CUDA copy and synchronization reference.

Solution. Keep the delay history and sample clock resident on the GPU. Upload changed coefficients and live parameters from pinned host memory. Clear the delay history only when the profile change explicitly requires a reset.

Why it worked. The broker can update the host-owned fields without first reading back the device-owned state. All 13 channel tests passed, including the matrix profile-history test. The untraced wireless rerun used the same TensorRT engine and initial robot state and checked the full 10-second window.

Debugging checklist

  1. Set the window. Warm up the model and radio, then use a common monotonic wall-clock window. Take counter snapshots before and after both boundaries, verify that the producer did not restart, and account for the age of the telemetry snapshot.
  2. Count the clocks. For UL and DL separately, take the change in completed slot equivalents divided by elapsed wall seconds. Report one-second bins and the minimum, plus the nominal slots due minus actual progress as drift. Record inter-completion gap p95, p99, and maximum where timestamps are available. Report deadline misses separately. For the robot, report physics and PD rates, simulation time versus wall time, new target cadence, and observation-to-PD latency.
  3. Trace the symptom. For rate dips, check input starvation, queue or output backpressure, and scheduler delays from runnable to running. For overruns, split each broker call into time before, during, and after CUDA synchronization. Correlate the calls with TensorRT and profile updates, and add probes around a suspect copy when the delay occurs before synchronization. Check trace overruns per CPU and separate traced calls from nominal slot estimates.
  4. Verify the change. Hold the scenario, engine, initial state, and measurement window fixed. Verify applied CPU and MPS placement. Use tracing to locate the cause, then remove the probes for the final counter-based comparison. Report timing, radio delivery, and robot motion separately.
