Wi-Fi access point beside a campus Wi-Fi connection — 2026-10-08

A Linux workstation whose only network link is a campus Wi-Fi connection (WPA2-Enterprise, PEAP) also runs its own Wi-Fi access point on the same card. The PC routes the access point's clients to the internet through the campus connection and hides them behind NAT.

October 8, 2026

Result

  • The campus Wi-Fi connection stays up while the access point runs.
  • Clients of the access point get addresses in 10.42.0.0/24, and their traffic leaves through the campus connection with the PC's address (masquerade NAT).
  • The campus network sees only the PC. New connections from the campus side into 10.42.0.0/24 are rejected, and IPv6 is off on the access point.
  • Clients can still reach the PC itself and other campus hosts, which see that traffic as coming from the PC.
  • The access point comes back at boot through a systemd service.

Hardware and system

  • Card: MediaTek MT7925 (Wi-Fi 7), driver mt7925e.
  • Ubuntu 24.04, kernel 6.8 (lowlatency), NetworkManager, Docker 29.
  • Client interface: wlp129s0, connected to campus Wi-Fi on channel 44 (5220 MHz).
  • Access point interface: wlap0, a virtual interface on the same radio.

Checking that the card can do both

iw list reports which interface types can run at the same time. The MT7925 reports this combination: 

#{ managed, P2P-client } <= 2, #{ AP, P2P-GO } <= 1,
total <= 2, #channels <= 2

One managed (client) interface and one AP interface fit within the total of two. The card can serve two channels, but it then has to switch between them, which roughly halves throughput on both. The access point therefore uses the same channel as the campus connection.

Problems and fixes

  • Regulatory domain. The kernel started in the world domain (country 00), which marks 5 GHz channels passive-scan only, so an access point cannot transmit beacons there. Setting the country to Singapore (iw reg set SG) allows an access point on channel 44.
  • Duplicate MAC address. A new interface created with iw ... interface add copies the parent's MAC address. wpa_supplicant then fails with "Name not unique on network" and NetworkManager shows the device as unavailable. Creating the interface with its own locally administered address fixes it. Set the 0x02 bit of the first byte of the parent's address, for example 58:... becomes 5a:....
  • Docker's FORWARD policy. Docker sets the iptables FORWARD policy to DROP. Clients joined, completed the WPA2 handshake and got a DHCP lease, then disconnected after about 50 seconds because none of their traffic was forwarded. Two ACCEPT rules in the DOCKER-USER chain fix it.

Configuration

<AP_MAC>, <SSID> and <PASSWORD> are placeholders.

Regulatory domain at module load

/etc/modprobe.d/cfg80211-regdom.conf

options cfg80211 ieee80211_regdom=SG

NetworkManager profile (created once)

sudo iw dev wlp129s0 interface add wlap0 type __ap addr <AP_MAC>
nmcli con add type wifi ifname wlap0 con-name pc-ap ssid <SSID> \
  802-11-wireless.mode ap 802-11-wireless.band a 802-11-wireless.channel 44 \
  802-11-wireless.cloned-mac-address <AP_MAC> \
  ipv4.method shared ipv6.method ignore \
  wifi-sec.key-mgmt wpa-psk wifi-sec.psk <PASSWORD>
nmcli con modify pc-ap connection.autoconnect no

ipv4.method shared makes NetworkManager run dnsmasq for DHCP and DNS on 10.42.0.0/24 and install an nftables table (nm-shared-wlap0) with the masquerade rule and the forward rules that reject new inbound connections. Autoconnect is off so that the boot service brings the profile up only after wlap0 exists.

Boot script

/usr/local/sbin/zg-ap-up.sh

#!/bin/sh
# Bring up the access point on a virtual interface beside the campus Wi-Fi client.
set -e
/usr/sbin/iw reg set SG
if [ ! -e /sys/class/net/wlap0 ]; then
    /usr/sbin/iw dev wlp129s0 interface add wlap0 type __ap addr <AP_MAC>
fi
for i in $(seq 1 30); do
    nmcli -t -f DEVICE dev | grep -qx wlap0 && break
    sleep 1
done
nmcli dev set wlap0 managed yes
sleep 2
nmcli con up pc-ap
# Docker sets the FORWARD policy to DROP; let AP clients out via campus Wi-Fi and replies back.
/usr/sbin/iptables -N DOCKER-USER 2>/dev/null || true
/usr/sbin/iptables -C DOCKER-USER -i wlap0 -o wlp129s0 -j ACCEPT 2>/dev/null \
  || /usr/sbin/iptables -I DOCKER-USER 1 -i wlap0 -o wlp129s0 -j ACCEPT
/usr/sbin/iptables -C DOCKER-USER -i wlp129s0 -o wlap0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT 2>/dev/null \
  || /usr/sbin/iptables -I DOCKER-USER 1 -i wlp129s0 -o wlap0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

systemd unit

/etc/systemd/system/zg-ap.service, enabled with systemctl enable zg-ap

[Unit]
Description=Wi-Fi access point beside campus Wi-Fi
Requires=sys-subsystem-net-devices-wlp129s0.device NetworkManager.service
After=sys-subsystem-net-devices-wlp129s0.device NetworkManager.service docker.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/local/sbin/zg-ap-up.sh
ExecStop=-/usr/bin/nmcli con down pc-ap
ExecStop=-/usr/sbin/iw dev wlap0 del

[Install]
WantedBy=multi-user.target

After=docker.service only orders the service after Docker when Docker is installed. It does not require Docker.

Working safely over a single Wi-Fi link

Wi-Fi was the PC's only network link, so a driver fault would also cut the SSH session used for the setup. Before each change, a systemd timer was armed to undo it after five minutes: 

sudo systemd-run --on-active=300 --unit=ap-rollback /bin/sh -c \
  'nmcli con delete pc-ap; iw dev wlap0 del; nmcli dev connect wlp129s0'

The setup commands also ran as a detached unit (systemd-run), so a dropped SSH session could not interrupt them halfway. The timer was cancelled once both connections were confirmed working.

Checks

nmcli -t -f DEVICE,STATE,CONNECTION dev | grep ^wl   # both connected
iw dev wlap0 info                                     # type AP, channel 44
iw dev wlap0 station dump                             # joined clients
sudo nft list table ip nm-shared-wlap0                # NAT and forward rules
sudo iptables -L DOCKER-USER -v -n                    # forwarded packet counters
systemctl status zg-ap

Verified on 2026-10-08. The PC kept internet access over campus Wi-Fi, a client joined the access point and passed traffic through the DOCKER-USER rules, and restarting the service recreated the access point. A full reboot has not been tested yet.
